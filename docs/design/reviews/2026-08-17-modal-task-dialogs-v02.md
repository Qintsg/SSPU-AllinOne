# 清源任务型模态框 v02 评审记录

日期：2026-08-17  
分支：`feature/design-language-spec`  
状态：设计参考已评审并冻结

## 修订原因

v01 的 HTML 参考可以完整展示六个字段，但真实 Flutter 在 360×800 的 content 状态中，滚动窗口恰好停在“单次抓取数量”标签与输入框之间。虽然内容仍可滚动到达，这个断点会让用户误判字段是否可操作，也割裂了两个请求限制参数的协同关系。

## v02 方案

- Cookie、Token、App ID、User-Agent 四个认证字段继续单列排列，保留从身份信息到客户端信息的阅读顺序。
- “单次抓取数量”和“请求间隔（毫秒）”在紧凑端同行，构成一个明确的请求限制语义组。
- 两个输入框仍维持 48dp 最小触控高度；不通过缩小目标或字号换取空间。
- 任一数值字段出错时，错误留在字段原位，另一个字段和前四个字段都不得清空。
- 768 及以上继续采用既有双列表单，不改变字段顺序、保存返回值或业务校验。
- 宽屏双列按行优先组织语义与焦点树，Tab 顺序保持 Cookie → Token → App ID → User-Agent → 单次抓取数量 → 请求间隔。

## 自评审

否决“继续六字段单列并依赖用户滚动”的方案，因为它在首屏中间留下不完整控件；也否决“压缩所有输入高度”的方案，因为它会损害触控与键盘操作。本方案只对具有同一业务含义、值较短的两个字段建立同行关系，是最小且可解释的布局变化。

冻结要求：`settings.wechat-config` 的四档视口、亮暗主题、content 与 validation-error 共 16 张浏览器参考全部生成；360×800 不出现横向溢出，两个请求限制字段完整同行，错误提示位于行动区上方；1200×900 继续保持双列密度。验收跳过 SSIM，采用产物完整性和人工逐屏复核。

## 浏览器核验与冻结结论

- `build/design-review-wechat-config-v02` 已生成 16/16 张参考图。
- 360×800 亮暗主题的 content 与 validation-error 均完整显示两个请求限制字段；标签没有横向溢出，48dp 输入高度保持不变。
- 数值错误停留在对应字段原位并位于行动区上方，另一数值字段及四个认证字段保持可见。
- 1200×900 暗色内容与错误态继续采用双列密度，表单没有新增卡片层级或无意义留白。
- 页面底层设置上下文仍可辨认，模态四边保持安全边距。

本稿取代 v01 的微信配置紧凑端布局规则并正式冻结；密码模态继续沿用 v01 冻结规则。Flutter 实现不得通过缩小目标、隐藏字段或改写业务校验规避布局约束。
